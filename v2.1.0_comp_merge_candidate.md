# v2.1.0_comp_merge_candidate

## What is Cutter Compensation

Cutter compensation applies a lateral offset to the programmed toolpath to account for the physical cutter edge diameter, ensuring the tool follows the intended "real" geometry. More here..(/link to Nist reference or similar).

- G41: tool-left compensation.
- G42: tool-right compensation.
- G40: compensation cancel / return to nominal path.

Conceptually, compensation transforms coordinates within gcode motion commands such as G1 X(2.123) by recognizing the direction of travel and then applying a perpendicular offset of the intended ("real") tool radius, while preserving junction continuity at line or arc transitions.

To visualize the effect of compensation: imagine a multilane highway representing the programmed toolpath. The center lanes on each side of the highway are the nominal path. When G41 or G42 is activated, the tool shifts to the left or right lane to accommodate the vehicle's size (tool diameter) and avoid crashing into the barriers on either side (the finished edges of the part).

The direction of travel relative to the inside road barrier determines whether G41 or G42 is appropriate. If the vehicle is driving in the fast lane in the EU we would call this climb cutting, and if it were driving in the fast lane in the US we would call it conventional cutting. Respectively, driving in the slow lane is conventional in the EU and climb cutting in the US. Keep in mind that cutter rotation direction is always clockwise, kind of like a helical wind turbine fastened to the top of your vehicle.

The compensation logic needs to know which side of the programmed path the tool should be on, so it can apply the offset in the correct direction to the correct side of the finished edge of the part.

## Architecture

### Dual ring-buffer with lookahead

Compensation needs local lookahead to determine travel direction, so the preprocessor keeps two synchronized fixed-size rings:
- Uncompensated ring: source-of-truth programmed points.
- Compensated ring: generated, execution-ready offset output, backed by a preallocated `Gcode` pool to avoid per-move heap churn.

Incoming motion fills the uncompensated ring; once enough context exists, offset geometry is solved, queued to the compensated ring, and drained through the normal Robot execution path. Memory is bounded, the G40 flush is deterministic, and the stage is single-writer.

### A-B-C corner model

Corners are solved from three points — A (previous), B (junction), C (next):
- Onset (A==B): initial perpendicular offset from the outgoing tangent.
- True corner (A,B,C distinct): intersection of incoming/outgoing offset lines (miter-consistent).
- Terminal (B==C): terminal perpendicular offset for a clean exit.

One geometric rule-set for all junction classes removes the per-case drift and diagonal artifacts of earlier multi-path logic.

### Arc compensation

- Supports `G2`/`G3` with I/J center in G17.
- Effective offset radius is derived from the uncompensated radius and tool radius with side-aware sign; endpoints are kept consistent to avoid snap artifacts.
- R-format arcs under active compensation are rejected rather than silently mis-cut.

## Tool Diameter and Wear (D-word workflow)

Compensation needs an effective tool diameter, resolved as:

1. A `D` word on the `G41`/`G42` block (full nominal diameter), if present; otherwise
2. The stored `TOOL_DIA`, entered manually via `M493.3 D<mm>`.

An additive wear term `TOOL_DIA_WEAR` (set via `M493.3 W<mm>`) is always added to the nominal: `effective_diameter = nominal + wear`, `radius = effective_diameter / 2`. `M493.4` reports both stored values. Diameter and wear are latched while `G41`/`G42` is active — attempts to change them during an active, playing compensation are rejected (issue `G40` first). Both EEPROM fields are range-validated on load to reject stale/garbage values inherited from older firmware.

> The automated `M491.x` toolsetter diameter-measurement / "certification" path is **not** part of this branch — diameter is operator-supplied. EEPROM storage is a temporary home pending a future SD-backed tool table.

## Fusion 360 CAM Notes

Fusion offers five compensation types: In Computer, In Control, Wear, Inverse Wear, and Off. Cutter comp adjusts the toolpath at the machine to account not only for tool size, but also tool wear and deflection.

**This branch supports In Computer (Off) and In Control** (full `G41`/`G42` with a D-word, or stored `TOOL_DIA` fallback). **Wear / Inverse Wear are not supported** because they require a per-tool *nominal* diameter baseline (`effective = nominal_radius + D_delta`) that only a tool table can supply — neither the firmware nor the Carvera controller has one yet, so a Wear-mode D-word would silently mis-offset. There may be opportunity to add Wear / Inverse Wear support if the nominal tool is provided by the Fusion 360 post.

Post-processor guidance for finishing paths: https://www.autodesk.com/products/fusion-360/blog/cutter-compensation/
- Cutter comp must be toggled on a line move, never an arc: issuing `G40`/`G41`/`G42` on a `G2`/`G3` is a compensation error that halts the program.
- Do not enable `G41`/`G42` during rapids or pure Z approach/retract.
- Emit `G41`/`G42` just before the first XY cutting lead-in at depth; keep it active through the contour; emit `G40` only after a dedicated XY lead-out, then retract.
- Lead-in/out should be explicit XY cutting moves ≥ tool radius (1.5–2× preferred). The pipeline is a lookahead intersection solver, so short/ambiguous transition moves around the toggle produce lead-in/out artifacts even when the contour body is accurate.

D-word semantics: in standard CNC (RS274/NGC, Fanuc, Haas) the D-word is **not a dimension** — it is a small integer that selects a row in the control's tool / diameter-offset table, and the control looks up the actual radius from that row. For example, `G41 D2` means "compensate left using the diameter stored in offset register 2." Loading the full radius into that row gives *In Control*; loading only the wear delta gives *Wear*. This firmware has no offset table, so it instead treats the **D value as the literal tool diameter in mm** (closer to LinuxCNC's dynamic `G41.1`/`G42.1 D<diameter>` form). The article's feature-size "dial-in" (e.g. a 1.000 in boss measuring 1.001 in, trim by 0.001 in) therefore maps here to the additive wear term via `M493.3 W`, rather than editing an offset register.

> Convention note: this firmware follows the RS274/NGC / Fanuc / LinuxCNC standard: **G41 = left**, **G42 = right** (relative to direction of travel). The linked Autodesk blog labels them the opposite way (G41 = right, G42 = left); that labeling is non-standard, so trust the standard convention when configuring a post or reading the blog.

The compensation **mode** (full vs. wear) should ultimately be a machine-level `config` setting, not dictated by CAM alone — pending tool-table support.
